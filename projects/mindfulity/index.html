Mindfulity

Navigate life’s transitions — and transform them.

A life-transformation platform for people moving through loneliness, burnout, job loss, career transition, financial uncertainty, and reinvention — combining education, coaching, community, and wellness resources in one calm, unified experience. Built on Next.js 15 and Supabase, with a multi-agent AI pipeline that turns a raw draft into a published, taxonomy-tagged article.

The Problem

Why I built this

A career in semiconductors and hardware — industries that restructure in waves. I watched capable people lose roles for reasons that had nothing to do with the quality of their work, then try to rebuild across a dozen disconnected tools that each knew one tenth of their situation. Mindfulity is the platform I wanted to be able to hand them.

Life transitions are handled by fragmented tools that each solve one tenth of the problem.

Someone who loses a job at 55 needs career help, financial guidance, and mental-health support at the same moment — and today that means a job board, a budgeting app, a therapy directory, and a dozen browser tabs, none of which know about each other. Mindfulity treats the transition itself as the organizing unit, not the service category.

Fragmented

Career, financial, and mental wellness resources live in separate products that never share context.

Transactional

Most platforms optimize for a conversion event, not for someone’s eighteen-month recovery arc.

Content-starved

Quality guidance for these moments is expensive to produce, so platforms ship thin libraries that go stale.

Multi-Agent Content Pipeline

Drop a raw markdown draft into content/_inbox/ and four specialized agents take it from there — writing, tagging against the taxonomy, and committing the published article. Click a stage to see what it owns.

Platform Taxonomy

Ten modules spanning the full arc of a life transition. The schema separates taxonomy from content — categories and subcategories are many-to-many, so a single article on burnout can surface under Mental Wellness, Career Recovery, and Transformation without being duplicated. Select a module to explore it.

Architecture

The design decision the project rests on: pages never touch the filesystem or the database directly. Everything goes through a ContentProvider interface, so the storage backend is a one-line swap.

Presentation

Next.js 15 App Router

React 19 server components, static generation for article routes, Tailwind for styling. Dynamic [module] and articles/[slug] segments driven by config.

Abstraction

ContentProvider interface

A single contract in lib/content/provider.ts. Two implementations ship — MDX filesystem and Supabase Postgres — and the platform has already migrated across them without a page component changing.

Data

Supabase

Auth with OAuth callback handling, Postgres holding the category/subcategory/module taxonomy, and storage. Typed end-to-end against the generated schema.

Automation

Agent workflow

Four Claude agents defined as markdown specs in .claude/agents/, invoked by a publish script that writes straight into the content store.

      The ContentProvider seam5 methods · lib/content/provider.ts
      

        
The architectural bet of the project. Pages depend on this interface and nothing else, so storage is a
          swappable detail. Both implementations exist — and the swap has already been exercised in
          production, which is the part that matters: the platform now runs on Supabase, and not one page
          component changed when it moved off MDX.


export interface ContentProvider {
  /** List content matching a query. Only published+public unless overridden. */
  list(query?: ContentQuery): Promise<AnyContent[]>;

  /** Fetch a single content object by type + slug. */
  getBySlug(type: ContentType, slug: string): Promise<AnyContent | null>;

  /** Fetch an article (with rendered body) by slug. */
  getArticle(slug: string): Promise<Article | null>;

  /** All article slugs — used for static generation. */
  articleSlugs(): Promise<string[]>;

  /** Related content — admin overrides, then shared tags, then category. */
  related(item: AnyContent, limit?: number): Promise<AnyContent[]>;
}

        
That last method is the Content Relationship Engine: resolution honours manual
          relatedIds first, then shared tags and keywords, then same-category fallback — so
          editorial intent always beats the algorithm.

      

    


    

      Universal Content Model15 content types · one shape
      

        
Every object on the platform — article, course, coach, travel package, testimonial — shares
          one base shape and extends it. This is what lets a single taxonomy, a single relationship engine, and a
          single provider interface serve wildly different content without special-casing.


export type ContentType =
  | "article"   | "video"    | "podcast"  | "download"
  | "resource"  | "product"  | "service"  | "course"
  | "webinar"   | "workshop" | "event"    | "travel-package"
  | "coach"     | "speaker"  | "testimonial";

export type PublishStatus = "draft" | "scheduled" | "published" | "archived";
export type Visibility    = "public" | "members" | "private";

export interface BaseContent {
  id: string;  type: ContentType;  slug: string;  module: ModuleId;
  title: string;  summary: string;  description?: string;
  category?: string;  subcategory?: string;
  tags: string[];  keywords: string[];
  /* …featuredImage, gallery, SEO fields, status, visibility */
}

        
Pages depend only on these types — never on where content physically lives.

      

    


    

      Postgres schema & row-level security2 migrations · 5 roles
      

        
The taxonomy from the vision document, expressed as real Postgres. Five user roles, enum-constrained
          content types mirroring the TypeScript union, and a profiles table that auto-populates from
          auth.users via trigger. RLS policies ship in the second migration.


create type user_role as enum (
  'visitor', 'member', 'coach', 'vendor', 'admin'
);

create type content_type as enum (
  'article', 'video', 'podcast', 'download', 'resource', 'product',
  'service', 'course', 'webinar', 'workshop', 'event', 'travel_package',
  'coach', 'speaker', 'testimonial'
);

create type publish_status  as enum ('draft','scheduled','published','archived');
create type visibility_level as enum ('public','members','private');
create type booking_status   as enum ('pending','confirmed','cancelled',
                                        'waitlisted','attended');

create table profiles (
  id         uuid primary key references auth.users (id) on delete cascade,
  full_name  text,
  role       user_role not null default 'member',
  created_at timestamptz not null default now()
);

        
The booking_status enum is the seam for the Services module —
          coaching and workshops are bookable objects in the same content model, not a bolted-on subsystem.

      

    


    

      How an agent is actually definedmarkdown spec · 4 agents
      

        
Each pipeline stage is a markdown file with frontmatter declaring its tools, model, and contract.
          No orchestration framework — the specs are the program. Here is the real content-manager header:


---
name: content-manager
description: >-
  Packages finished article content into a schema-valid staging file for
  publishing. Use after content-creator produces body + suggested metadata.
  Builds Universal Content Model frontmatter, picks the URL slug and SEO
  fields, and writes a staging file to content/_inbox/. Does not publish
  (that's code-dev, which inserts it into Supabase).
tools: Read, Write, Edit, Glob, Grep, Bash
model: opus
---

        
Note the explicit non-responsibility — does not publish. Each agent's spec
          names what it must not do, which is what keeps a four-stage chain from collapsing into one agent that
          does everything badly.
